# LendLoop Constitution

LendLoop is a neighborhood tool-lending app built as a learning project.
Its three goals are learning FastAPI, learning Next.js, and practicing
spec-driven development. When a choice trades convenience against
understanding, choose understanding.

## Core Principles

### I. Spec Before Code

- Every feature starts as a spec under `specs/`, and implementation follows
  the order specify → clarify → plan → tasks.
- Specs describe behavior (what and why) and never name technologies.
  Technical decisions belong in `plan.md`.
- If implementation shows the spec is wrong, update the spec first, then
  the code. The spec and the code must never disagree.
- Why: the spec is the source of truth. A spec that drifts from the code is
  worse than having no spec.

### II. Server-Side Enforcement (NON-NEGOTIABLE)

- The backend enforces every authorization rule: roles, ownership, and
  valid state transitions.
- The frontend may hide or disable actions as a convenience, but it is
  never the security boundary.
- Ownership is checked in the data query itself (for example, filtering by
  owner), not only after the record has been loaded.
- Why: the UI can be bypassed; the API cannot.

### III. Explicit API Contracts

- Database models are never returned directly from an endpoint. Every
  response uses a dedicated response schema.
- Public (unauthenticated) responses expose only the fields the spec allows.
- Each feature's API is documented in `contracts/` before it is built. The
  OpenAPI schema generated by the backend is the contract the frontend uses.
- Why: this prevents data leaks such as password hashes or owner details,
  and keeps the frontend and backend in sync.

### IV. Test-First Development

- Every acceptance criterion in a spec maps to at least one automated test.
- Backend:
  - Tests are written before the code they test (red → green → refactor).
  - Tests run against a real PostgreSQL database, not SQLite or mocks.
  - Authorization rules have explicit negative tests: user A cannot act on
    user B's data, and non-admins cannot reach admin actions.
- Frontend:
  - Component tests cover every Client Component that has behavior
    (forms, validation, conditional rendering, user interactions).
  - Tests check what the user sees and does (roles, labels, text), not
    implementation details.
  - Async Server Components are kept thin. Their logic lives in plain
    functions that can be tested on their own. End-to-end tests are out of
    scope for now and will be added by amendment.
- Why: tests turn the spec into something executable, and negative tests
  are the only proof that access control works.

### V. Secure by Default

- Secrets come only from environment variables or the secret store of the
  service that needs them. They never appear in code, committed files, or
  exported workflow definitions.
- Calls between systems (backend ↔ automation workflows) are signed and
  verified, and are rejected if the signature is missing, invalid, or stale.
- Any write that may be retried is idempotent, enforced by database
  constraints rather than application checks alone.
- Authentication is built in-house. No third-party identity provider is used.
- Why: the project exists to understand these mechanisms, so they must be
  done properly.

### VI. Failures Are Visible

- No error is silently swallowed. Failed background or automation work is
  recorded somewhere a person can see it.
- Outbound notifications are delivered reliably: they are persisted together
  with the change that caused them, and retried if delivery fails.
- Why: automations that fail silently are worse than having none.

### VII. Small, Learnable Increments

- Each task is small enough to finish and understand in one sitting
  (about an hour or less).
- Each task notes the FastAPI or Next.js concept it practices.
- Prefer framework-native solutions over extra libraries unless the plan
  justifies the dependency.
- Why: the main goal is learning, so every unit of work should teach
  something and be fully understood before moving on.

### VIII. Human-Written Core, AI-Assisted Edges

- AI agents MAY generate:
  - project scaffolding and configuration (Docker, Alembic setup, tooling
    config, CI)
  - boilerplate (empty modules, `__init__` files, generated API clients)
  - test cases and test fixtures
  - UI primitives installed through shadcn/ui
- The developer writes by hand:
  - endpoints, dependencies, and authorization logic
  - authentication and security mechanisms
  - business rules and state transitions
  - database models and queries
  - Next.js pages, layouts, data fetching, and feature components
- Every task in `tasks.md` is labeled `[AI]` or `[HUMAN]`.
  `/speckit-implement` carries out only `[AI]` tasks. For `[HUMAN]` tasks,
  AI explains concepts, reviews code, and suggests changes, but does not
  write the implementation.
- A human reads every AI-generated test and understands it before relying
  on it.
- Why: the developer learns the frameworks by writing the code that matters.
  AI speeds up the parts that teach nothing new.

## Technology Constraints

- Backend:
  - Python 3.12+, FastAPI, SQLModel with synchronous sessions, Alembic,
    PostgreSQL 16+.
  - Tooling: uv for dependencies, Ruff for linting and formatting, pyright
    in standard mode for type checking, pytest for tests.
- Frontend:
  - Next.js (App Router) with TypeScript in strict mode.
  - Styling: Tailwind CSS and shadcn/ui. No other component or styling
    libraries without a justification in the plan.
  - Tests: Vitest and React Testing Library.
- Automation: n8n.
- Local environment: Docker Compose starts everything with one command.
- Database schema changes happen only through Alembic migrations.

## Development Workflow

- One feature per branch, matching its spec folder (for example, `001-accounts`).
- Commits are small and reference the task ID they complete.
- A feature is done when:
  - every task is checked off
  - all backend and frontend tests pass
  - Ruff, pyright, ESLint, and the TypeScript compiler report no errors
  - the spec matches what was built

## Governance

- This constitution overrides any conflicting spec, plan, or task.
- Amendments are made through `/speckit-constitution`, with a version bump:
  MAJOR when a principle is removed or redefined, MINOR when one is added,
  PATCH when wording is clarified.
- Every plan includes a constitution check, and any violation is either
  fixed or explicitly justified in that plan.
